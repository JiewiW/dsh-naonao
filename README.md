# dsh-naonao

> 唠叨模式：把临时提醒/临时要求挂在输入框上，每轮自动注入到模型上下文末尾；用完一键清除。

一个 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）插件。Web 端在输入框左下角加一个「唠叨」按钮，点开是一张双栏编辑卡：左边写、右边看当前已保存内容与 token 粗估。

典型用途：

- 「本轮所有回复用简体中文」「先给结论再给过程」这类**临时**风格/格式要求；
- 「不要动 X 目录」「改完先跑某测试」这类**只对当前任务有效**的约束；
- 任何你不想写进长期记忆、也不想每轮手动粘贴的话。

它不是记忆插件：内容只存在内存里、只属于当前会话，会话结束即消失。

---

## 快速开始

```sh
dsh plugin --profile <你的profile> add github:JiewiW/dsh-naonao#v0.1.0
```

安装后重启 DSH 实例，输入框左下角出现「唠叨」按钮即已生效。

卸载或停用后不会残留任何文件——插件本身不落盘（见下文「工作原理」）。

## 使用

1. 点输入框左下角「唠叨」，展开编辑卡；
2. 左栏写提醒内容，点「保存」——从下一轮请求开始生效；
3. 右栏实时显示当前已保存内容，并给出 token 粗估评级：

| 评级 | 估算 token | 含义 |
| --- | --- | --- |
| 轻量 | ≤ 30 | 约占 1% 上下文，几乎不影响 |
| 适中 | ≤ 100 | 约占 2–3%，影响可控 |
| 较重 | ≤ 300 | 约占 5–10%，可能稀释注意力 |
| 过重 | > 300 | 超过 10% 上下文，建议精简 |

（token 估算口径：中文字符数 / 1.5 + 其他字符数 / 4，仅作量级参考。）

4. 临时需求做完后点「清除」，此后新请求不再携带该内容。

### 跟直接发消息/插话怎么选

唠叨不是消息通道——它是一条持续生效的约束通道。想"给正在干活的模型递一句话"时，先想清楚你要的是哪一种：

| 场景 | 用唠叨（改内容保存） | 用输入框直接发/插话 |
| --- | --- | --- |
| 本轮剩余工作都要遵守的约束（"全程中文""别动 D:\xxx""改完先跑测试"） | ✅ 持续生效、不打断执行流，用完即清除 | ❌ 一次性，模型处理完这条就不再携带 |
| 紧急纠正、追问、澄清（"停，别删那个文件"） | ❌ 无确认反馈——模型把它当背景约束读取，不会回应，你只能事后看行为 | ✅ 模型会显式回应，你能立刻确认它收到并开始处理 |
| 不想打断模型当前思路、只是补一条背景要求 | ✅ 后台注入，几乎零干扰 | ❌ 注意力切换真实存在 |
| 需要模型确认理解了（"听明白了吗？"） | ❌ 无确认反馈 | ✅ 模型会显式回应 |

三条机制边界（想用唠叨递话前必须知道）：

- **生效时机不是立刻**：唠叨挂在下一个请求组装时注入，具体时间取决于模型当前执行段的剩余时间；
- **模型不会显式回应**：它按"本轮必须遵守"的背景约束执行，遵守与否要看行为，不是看回复；
- **挂着的成本**：合并快照每步重发时，唠叨搭车全价重读；用完即清除更省（详见下文「缓存成本」）。

## 工作原理

### 挂载点：动态 context，不是 system prompt

Host 端通过 DSH 的动态上下文注册点挂载：

```js
ctx.systemPrompt.context({
  name: 'dsh:naonao',
  order: 100000,
  text: () => getNaonaoText(sessionId),
})
```

这与「往 system prompt 里加一段」有本质区别：

- **system prompt 主体**是会话开头的稳定前缀，字节不变才能全程命中前缀缓存；
- **动态 context** 是独立通道。DSH 内核把所有插件贡献的动态 context（沙箱策略、审批策略、子代理委派说明、记忆快照、唠叨……）按 `order` 排序，**合并成一条快照**，以 `user` 角色消息追加在当批消息末尾，固定开头为：

  ```
  Current runtime context. This snapshot supersedes earlier runtime-context snapshots.
  ```

- naonao 的 `order = 100000`，排在所有内置 context 之后。注入时的包裹格式固定：

  ```
  ---

  ## 用户唠叨（本轮必须遵守）

  <你写的内容>

  ---
  ```

### 去重：快照全文不变就不重发

内核（`RuntimeContextProjection`）对合并快照做全文比对：**只有合并后的快照与上一次不同，才追加一条新的 user 消息**；完全相同则什么都不发。naonao 自己保存一份不变的文本，不会单独触发重复注入。

### 存储与接口

- 文本保存在 Host 进程的 per-session `Map<sessionId, text>` 里，纯内存；
- Web 端通过三个 RPC 读写：`naonao/get`、`naonao/set`、`naonao/clear`，只有手动点「保存 / 清除」才会调用，没有任何每轮自动重发；
- 请求体硬上限 300KB；
- 会话 `disposed` 时从 Map 删除。重启进程或切换会话后内容都不存在。

注意：快照作为 user 消息会进入 DSH 的会话持久化日志——这是内核的消息落盘行为，插件自己不写任何文件。

### 「清除」不是删除旧消息

清除时内核不会改写或删除历史里已经发出的快照，而是追加一条固定声明：

```
Current runtime context: none. Earlier runtime-context snapshots no longer apply.
```

旧快照物理上仍在会话历史中，只是被声明失效。

## 缓存成本：这是本插件最需要讲清楚的部分

结论先行：**set 和 clear 都是尾部追加，都不会击穿前缀缓存；但「一直挂着」和「用完即 clear」在实际账单上有差异，临时需求用完即清除严格更省。**

### 为什么不击穿前缀缓存

前缀缓存只认请求开头连续未变的 token。唠叨快照是追加在请求**尾部**的 user 消息，它之前的 system prompt 与全部历史消息字节不变，前缀命中不受影响；新快照自身在首次出现的请求上按未命中计费一次。

### 真正的坑：合并快照是「拼车」的

naonao 不是一条独立消息，它和其他所有动态 context **共用同一条合并快照**。内核的去重粒度是整条快照：**任一贡献者变化，整条快照就重发**。

实际环境中，`dsh-auto-memory` 等插件贡献的记忆快照几乎每步都在变（完整快照与精简快照按轮次轮换、日志尾部每轮微变、唤回条目投递后翻转），于是：

- **一直挂着**：即使唠叨文本一个字没改，它也会搭车出现在每一步重发的整条快照里，按全价文本随快照重复计费；
- **用完即 clear**：新快照不再包含唠叨文本。历史里的旧快照仍然物理保留，但此后只是作为稳定前缀按缓存命中价重读，不再产生新的全价副本；
- **频繁 set/clear 抖动**：每次切换本身都让快照变化、强制追加一条新快照，是三种用法里最差的，应避免。

量级参考：一条 100 字的中文唠叨粗估 60–70 token，单次可忽略；但在一个几十步、且记忆快照每步重发的长任务里，挂着不动意味着它被全价重读几十次。

### 与 cot-anchor 类插件的区别

`dsh-cot-anchor` 注入的是独立的 user 通知消息（每条带唯一 ID、不走合并快照、每个工具步都可能出现）；naonao 走的是合并快照通道，自己不变化不触发注入，但会被同车的其他贡献者「带」着重发。两者机制不同，账单特征也不同。

## FAQ

**重启 DSH 后唠叨内容还在吗？**
不在。纯内存、per-session，进程重启或会话结束即清空。

**会上传或持久化到磁盘吗？**
插件自身不落盘任何文件。内核会把快照作为普通 user 消息写进会话日志（与你发的其他消息待遇相同）。

**为什么用动态 context 而不是直接加进 system prompt？**
为了让 system prompt 保持字节级稳定、全程命中前缀缓存。动态内容走 context 通道是 DSH 生态的既定分工。

**能写多长？**
RPC 硬上限 300KB，但 UI 的建议是控制在 300 token 以内——它每步都占模型注意力，写太长既费钱又稀释指令强度。长要求更适合写进项目规则或长期记忆。

**多会话互相影响吗？**
不影响。文本按 sessionId 隔离。
